# Changes — 30 September 2026

What was built and fixed in the 30 September working session, what each change
needs in order to work, and what is still open.

**Verification status.** Typecheck, lint (0 errors) and the unit tests pass, and
the backend starts and serves the new routes. None of the flows below has been
run end to end on a phone, and the admin panel changes have not been clicked
through. Treat everything here as built but untested until that is done.

---

## 1. Booking: customer to merchant, end to end

Before this session a customer's "booking" was written to `availability_requests`,
which only the admin panel read. The merchant never saw it.

| Step | Now |
|---|---|
| Customer books | Creates one pending row per service in `bookings`, linked to their account |
| Merchant sees it | "Needs your reply" queue on the Bookings tab, whatever day is selected |
| Merchant accepts | Picks a time slot; the booking moves onto that day's schedule |
| Customer is told | In-app notification with the agreed date and time |
| Sale is recorded | The booking counts in the merchant's Sales tab |
| Customer cancels | From the Activity tab; the merchant gets a "Cancelled by customer" alert |

Details:

- **Login is required to book.** A signed-out visitor can fill the form in and is
  sent to log in before it is submitted.
- **The customer picks a time of day, not a slot.** The merchant sets the real
  time when accepting.
- **Declining passes a reason** to the customer. Accept and decline can both be
  undone from a toast, which also withdraws the customer's notification.
- **Status changes are enforced on the server.** A booking the customer cancelled
  is final. Bookings for past dates are rejected (judged in Nairobi time).
- **Bookings a merchant enters by hand start as confirmed.**
- **The dashboard refreshes every 20 seconds** and when the app returns to the
  foreground, so Bookings, the tab badge and Sales stay current on any tab.

Key files: `backend/src/services/consumer-bookings.js`,
`backend/src/services/merchant-bookings.js`, `app/booking/[providerId].tsx`,
`app/(tabs)/activity.tsx`, `app/merchant/(dashboard)/bookings.tsx`,
`src/merchant/bookings-context.tsx`.

## 2. Merchant Bookings tab redesign

Rebuilt on `Inspo/Bookings Redesign.html`: reply queue with a count, "NEW · 2h"
tags, time-slot picker limited to the customer's preferred part of the day,
decline reasons, undo toast, compact day schedule, collapsing "New booking"
button. Kept from the old screen: booking details sheet, call and WhatsApp,
mark completed, cancel, change time. Slots that overlap another confirmed
booking are flagged as busy.

## 3. Sales

- **Accepted bookings count as sales automatically** (confirmed or completed,
  dated on the appointment day). Pending bookings are shown as "will count once
  you accept"; cancelled ones drop out.
- **Daily / Weekly / Monthly now work.** The switch scopes the totals, chart and
  transaction list; previously it only changed the highlighted pill.
- **Hand-entered transactions and targets are saved to the account**, not the
  phone. Whatever was on the phone is uploaded once on first load.

Key files: `app/merchant/(dashboard)/sales.tsx`, `src/merchant/sales-context.tsx`,
`backend/src/services/merchant-sales.js`.

## 4. Notifications

A `notifications` table and a real Notifications screen, with an unread badge on
the Account tab bell. Sent when a merchant accepts, declines, reschedules or
completes a booking, and when an admin approves a business or requests changes.

These are **in-app only**. There are no push notifications: a user sees them when
they open the app.

## 5. Sign-in flow redesign

Rebuilt on `Inspo/KiliPicks Auth.html`: welcome screen, create account, log in,
and an "all set" screen. Adds show/hide password, a password strength meter,
errors under each field, a Privacy Policy checkbox, and a working "Keep me
logged in" (unticked means nothing is saved to the phone).

Left out because no backend exists for them: Google sign-in, phone sign-in and
the code-entry screen. "Forgot password?" shows "coming soon".

## 6. Security and data handling

- **Login tokens move to encrypted storage** (Android Keystore / iOS Keychain)
  via `expo-secure-store`. Needs an app rebuild; see section 9.
- **No signal no longer logs the user out.** Only a server rejection of the
  token ends the session.
- **Photos can be stored in Supabase Storage** instead of the server's local
  disk. Needs configuration; see section 9.
- **A secret was being written to the logs** by the analytics route. Removed.
- **CORS is closed in production.** No website can call the API unless listed in
  `CORS_ORIGINS`. The mobile app is unaffected.
- **Rate limits work behind a proxy** once `TRUST_PROXY_HOPS` is set.
- **Privacy notice rewritten** to describe what the app actually collects. It was
  written from the code and has **not** been reviewed by a lawyer.

## 7. Admin panel

Bugs fixed:

- **Suspending a merchant now locks them out** and takes their business offline.
  Previously they could keep using the dashboard through their customer login.
- **An unpublished business can no longer be booked.**
- **Publish is blocked** for a business with no active, bookable service.

One rule now decides whether a business is live: published **and** owner not
suspended (`backend/src/services/business-visibility.js`). Search, booking and
reviews all use it.

Added:

- **Bookings, notifications and hand-entered sales** are visible (read-only).
- **Review queue**: businesses carry a review status and can be filtered to
  "Awaiting review", newest first.
- **Request changes**: write the reason in "Review note", then run the action.
  The merchant is notified and sees the note on their profile with a resubmit
  button.
- **Merchants are notified on approval.**
- **Customers can be suspended.**
- **Photos can be removed** from a listing (and a customer's profile photo).
- Removed the dead "Availability requests" and "Looks" entries.

## 9. Setup still needed

1. **Rebuild the app** (`npx expo run:android`) so encrypted token storage takes
   effect. Until then tokens are stored the old way.
2. **Supabase Storage**: create a public bucket and set `SUPABASE_URL`,
   `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_STORAGE_BUCKET` in `backend/.env`.
   Until then uploads go to local disk, which most hosts wipe on redeploy.
3. **On the production server**: set `NODE_ENV=production` (activates the CORS
   restriction) and `TRUST_PROXY_HOPS` (usually `1`).
4. **Legal review of the privacy notice** before public launch.

## 10. Known gaps

- **Not tested on a device.** The first job is a full run-through on two phones.
- **Inbox and Looks tabs are still mock content**, including a permanent unread
  badge of 5 on Inbox.
- **No password reset, email verification or account deletion.** Deletion is
  promised in the privacy notice and is a manual job for now.
- **No merchant availability.** The "Availability" button does nothing, so
  customers can request any day or time.
- **No push notifications, no payments.**
- **Nothing alerts the admin to a new submission**; someone has to open the list.
- **One shared admin login**, with no attempt limit and no action log.
- **No automated tests** cover booking, cancelling, accepting, notifications or
  sales, and CI does not run anything against the backend.
- **The old availability-request endpoint and client file are dead code.**
- **Customer search is cached for 5 minutes**, so an admin suspend, unpublish or
  photo removal takes that long to show there.

## How to run

```powershell
npm.cmd run backend:migrate      # apply database migrations
npm.cmd run backend:dev          # API on http://localhost:3000
npm.cmd run backend:admin:dev    # admin panel on http://localhost:3050/admin
npx expo start                   # the app
```

On Windows PowerShell use `npm.cmd`, not `npm`, unless script execution has been
enabled.
